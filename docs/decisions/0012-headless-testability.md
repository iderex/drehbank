# 0012. Headless testability as a birth requirement

Status: decided. Raised in issue #14.

## Why now

A test that needs a screen or a privilege will not run in the gate, and a test
that does not run in the gate is not a test. This is settled before the first
test is written, because retrofitting it means rewriting whatever was written in
the meantime, and because the shape of the harness decides which measurements the
project is able to make at all.

## The four conditions

Every test in the default suite runs:

- with no display available,
- with no elevated privileges,
- in a container with no special capabilities,
- with no network.

Anything that cannot meet all four is not in the default suite. There is no
category of test that is in the suite and skipped on some machines, because a
skip inside the suite is a green line that means nothing and it is the shape this
document exists to prevent.

**No display** means no plotting during a test, no windowing or graphics package
anywhere in the dependency graph of the test binaries, and no interactive prompt.
The graph is what decides it rather than the direct dependencies, because the way
this condition breaks is transitively: a convenience crate pulls in a plotting
crate which pulls in a windowing system, and nothing in the change that added it
mentions a display.

**No elevation** means no privileged hardware counters, no huge pages requested
through a privileged path, no change to a system limit, no mounting, no service
or scheduled task, and no certificate or trust store modification. A test that
needs any of those is not made to work by asking for the privilege. It is moved
to the harness below, and if it cannot be moved it is skipped and the skip is
disclosed where a reader of the result will see it, never worked around.

**No special capabilities** means the suite runs as an unprivileged user with the
default capability set. The condition is on how the suite is invoked, so the
invocation is visible in the workflow file and not only in prose, which is what
issue #20 checks.

**No network** means no fetching a fixture at test time and no resolving a name.
Fixtures are in the tree or generated by the test. This one is also the last line
of the rule in 0013: a suite that cannot reach the network cannot accidentally
prove that the package does not either, but a suite that can reach it will
eventually contain a test that depends on it.

## The determinism rule

No test depends on the wall clock, on a random seed that is not fixed in the
test, or on the number of available cores.

The third is the one this package will actually break. The default pool size of
0009 is the available parallelism, which is a property of the machine, so a test
that takes the default is a test whose behaviour differs between the developer's
machine and the runner. Every test sets the pool size explicitly. 0009's
determinism requirement is stated over a fixed list of thread counts including
counts larger than the machine has, for the same reason.

A fixed seed means the seed is a literal in the test. A seed derived from the
clock, from the process id or from an environment variable produces a suite that
fails once a month and passes when anybody looks at it.

The rule is a condition on the suite and it is checked by running the suite twice
in the same job and requiring the reported results to match, which is issue #20's
fourth check. That catches a clock or an unfixed seed and it does not catch a
dependence on the core count, which is why the pool size is a rule here as well
as a check there.

## What moves out, and where it goes

Three kinds of work genuinely need more than the four conditions allow. None of
them is suppressed. Each is moved into one named place and says what it needs.

**Scaling runs.** The target case, order eight to ten in six variables, needs a
large machine and hours. Whether a machine that can run it is available for
recorded runs is an open entry in issue #2, and until that is answered the
honest response is a smaller recorded target rather than an extrapolation
published as a measurement.

**Measurements that want hardware counters.** Cache behaviour and instruction
counts need elevation on most hosts. They live in the same harness. Where a
counter is unavailable, the harness prints that the measurement was not made.
It does not substitute an estimate, and it does not report a derived number in
the column a measured one would have occupied.

**Long fuzzing and mutation runs.** These are bounded by time rather than by a
pass condition, so they cannot gate a pull request without making the gate's
duration a policy decision made by accident. They run on a schedule with a stated
budget, and the quality parity milestone is where that is set up, in issues #55
and #56.

## The harness, and what it is called

One workspace member, not built by the default build, called

    needs-a-large-machine

The name is the disclosure. A harness called `integration` or `bench` that
quietly wants tens of gigabytes is reported as broken by everyone who runs it on
a laptop, and after the third such report somebody deletes it. A harness whose
name says what it needs is one people either run deliberately or skip
deliberately, and a deliberate skip cannot be read as a pass.

## What it prints before it runs

Before any work, and before the first case, it prints:

- that it is not part of the gate, in those words, so that a red line below is
  read as a measurement and not as a failed check,
- the peak live set it has computed for the case it is about to run, in bytes,
  from the formula in 0005 evaluated at that order and that number of degrees of
  freedom, with the coefficient width from 0002,
- the pool size it will use and the parallelism it found,
- what the case is expected to cost in time, or that the cost has **not been
  measured** where no run of it has been recorded yet.

The peak live set is computed rather than quoted, which is the point. A hardcoded
"needs sixty-four gigabytes" is a number that was true of one case on one day and
goes stale silently. A number derived from the case in front of it is right for
every case, and it is the same formula the memory ceiling of 0009 refuses on, so
the harness and the driver cannot disagree about what a run will cost.

If the computed peak exceeds what the machine has, it says so and stops before
allocating anything, for the reason 0009 gives: a refusal before the group says
which order cannot be afforded and by how much, and a kill during the group says
nothing at all.

## What a skip prints

A skipped case prints that it was skipped, why, and what running it would cost.

    skipped: <case>
    reason:  <the condition that was not met>
    cost:    <the computed peak live set, the pool size, and the time, or "not measured">

The cost line is what makes the skip actionable, and it is why a skip is not
allowed to be a single word. A reader who sees only that something was skipped
learns nothing they can act on. A reader who sees what it would take can decide
whether to find a machine.

A skip is never silent and never removed to make output tidy. This is the same
rule as the one in 0008 about an estimate that could not be computed, and the
same rule as the one in 0013 about a check that has not landed: the negative
statement is the useful one and it survives every edit.

## What it costs, stated rather than skipped

The four conditions cost the project the easiest kind of evidence. A plot is the
fastest way to see that a normal form is behaving, and it is banned from the
suite. The replacement is that everything the plot would have shown is a number
compared against a fixture, which is more work to write and is the only kind of
evidence a gate can hold. Plotting remains available to a person outside the
suite and is not in the dependency graph of the test binaries.

Moving the scaling runs out costs coverage on the exact case the project claims.
Nothing in the gate exercises order ten in six variables, so the gate proves the
algorithm on small cases and the harness proves it at scale, and the two are
reported separately rather than blended into one number. Saying that plainly is
better than a gate that appears to cover the target case and does not.

The determinism rule costs the convenience of a default. Every test naming its
pool size is verbose, and the verbosity is what makes the suite mean the same
thing on every machine.

## What this document does not decide

It does not decide the parallelism model or the determinism requirement's exact
form, which is 0009. It does not decide the memory ceiling arithmetic the harness
prints, which is 0009, nor the peak formula it evaluates, which is 0005. It does
not build the check that refuses a suite violating any of this, which is issue
#20. It does not build the harness, which is issue #51. It does not decide the
schedule or the budget for the long runs, which is the quality parity milestone.
